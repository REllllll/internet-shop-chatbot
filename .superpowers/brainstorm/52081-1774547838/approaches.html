Which project structure approach fits best?

All use monorepo · Docker · SQLite (Kaggle dataset) · No auth

A

FastAPI-centric

FastAPI is the hub. It hosts the MCP server in-process, calls Claude API directly, and manages chat sessions. n8n handles secondary async tasks (indexing, logging). React talks only to FastAPI.

Pros

  • Simple — one Python process does most things
  • Easy to debug locally
  • Low latency (no extra hops)

Cons

  • n8n is underutilised
  • Business logic lives in Python, not visible in n8n canvas
frontend/ · backend/ · mcp-server/ · n8n/ · data/ · docker/
B

n8n-centric

React POSTs directly to an n8n webhook. n8n orchestrates everything: calls Claude API, calls the Python MCP server via HTTP, formats and returns responses. Python is a thin MCP-only service.

Pros

  • Visual workflow canvas shows full pipeline
  • Easy to modify logic without touching code
  • Great for demos

Cons

  • n8n webhooks add latency & complexity
  • Harder to stream responses to frontend
  • Tightly coupled to n8n internals
frontend/ · mcp-server/ · n8n/ · data/ · docker/
C

Hybrid — clear service boundaries ★ Recommended

FastAPI handles the chat API (SSE streaming to React) and runs the MCP server in-process. n8n owns the recommendation pipeline — product retrieval → ranking → explanation building. FastAPI calls n8n as a sub-workflow when a recommendation is needed.

Pros

  • Each service has one clear job
  • n8n canvas shows the full recommendation pipeline visually
  • FastAPI handles streaming & session cleanly
  • Matches your interim report architecture exactly

Cons

  • Two services to manage (FastAPI + n8n)
  • Slightly more Docker config
